# setup-wizard

One-time first-boot setup on the child computer, hooking into Omarchy 4's deferred first-boot provisioning. Implementation plan: vault note "Omarchy Kids - Implementierung Setup-Wizard"; progress tracked on the [Pairing & Setup Wizard project](https://github.com/users/jfuerwentsches/projects/3) (issues #16-#29).

## Status

**Phase 1 (bootstrap logic, no UI) is implemented and verified end-to-end in the dev VM (2026-08-29)** — see `bootstrap/`:

- `bootstrap/omarchy-kids-bootstrap` — main entry point, run as root:
  ```
  sudo omarchy-kids-bootstrap --child-user <linux-username> --child-name "<display name>" --tier <tier> [--theme <theme-id>] [--admin-user <name>] [--admin-password <password>]
  ```
- `bootstrap/lib/branding-tier.sh` — renders the child's name as a screensaver banner and calls `omarchy-kids-set-tier <tier> [theme]` (issue #19). The vault note's original plan (`omarchy ascii "<name>"`) doesn't match the real Omarchy 4.0.1 CLI — there's no text-to-banner command, only the interactive `omarchy branding screensaver <image|text|reset>`. This reproduces its `image` mode non-interactively: render an SVG with the name, rasterize with `rsvg-convert`, transcode with `omarchy-transcode-ascii --mode block --invert` (verified by hand first, see git history).
- `bootstrap/lib/account.sh` — creates the separate parent/admin account (default name `omarchy-kids-parent`) and removes the child's own, Omarchy-created account from `wheel` if it's a member (issue #16). No interactive password prompt yet — pass `--admin-password` or let it generate and print one once; the real parent-facing form (issue #27) replaces this. Also installs a narrow NOPASSWD sudoers grant (`/etc/sudoers.d/zz-omarchy-kids-getty-lockdown`) for exactly the getty-mask/unmask commands `omarchy-kids-set-tier` needs for its VT lockdown step — without it, that step silently no-ops once the child loses `wheel` (or even non-interactively before that, since a tty-less sudo call has nothing to prompt on), quietly disabling the kiosk's actual access-control boundary. Filename deliberately sorts last: sudoers is last-match-wins per exact command line, and the dev VM had a pre-existing broader `devchild ALL=(ALL) ALL` rule (in `/etc/sudoers.d/04_devchild`, a dev-only convenience — see `docs/dev-vm-setup.md`) that silently shadowed an earlier "00-"-prefixed filename here during testing.
- `bootstrap/lib/ssh-key.sh` — prepares `~/.ssh` for the child account (issue #17, revised 2026-08-29). No longer generates a keypair or stashes a private key: pairing (below) transfers only the Control Center's *public* key, so there's nothing sensitive to prepare here anymore.
- UFW's SSH allow rule is deliberately **not** duplicated here — `omarchy-kids-agent`'s package `post_install` already does it (see `agent/packaging/PKGBUILD`, `docs/agent-protocol.md`). The bootstrap script only logs a warning if UFW is active without it (issue #18).

**Pairing (issues #21-#24) has a working protocol implementation, verified end-to-end in the dev VM over the real network (2026-08-29)** — see `agent/pairing/` (built as part of the `agent/` Rust workspace, not this folder) and `docs/agent-protocol.md`'s "Pairing protocol" section for the full design and security rationale. `omarchy-kids-pairing serve` (child side) and `omarchy-kids-pairing pair` (a reference client standing in for the not-yet-built Control Center) speak a SPAKE2-authenticated exchange over mDNS discovery or a QR-code fallback; the Control Center generates its own SSH keypair and only the public half is ever transmitted.

**The first-boot hook (issue #27) is implemented** — see `first-boot/`:

- `first-boot/omarchy-kids-setup-wizard.service` — `After=omarchy-provision-owner.service`, `Before=display-manager.service`, gated on its own idempotency marker (`/var/lib/omarchy-kids/setup-wizard/done`). Research for this (issue #26): Omarchy 4 has no official first-boot extension point — the first-boot flow is one monolithic first-party script (`omarchy-provision-owner`) with no drop-in/callback point anywhere in it. This integrates via systemd unit ordering instead of a hook inside that flow.
- `first-boot/omarchy-kids-setup-wizard` — the parent-facing form itself, run as root on tty1 (no graphical session exists yet at this point). Deliberately simple (per issue #27's scope: not a kid-friendly UI, the audience is the parent). Detects the child account Omarchy's own first boot already created (can't reuse `/var/lib/omarchy/provisioning/setup-user` — that's deleted by `omarchy-provision-owner`'s own cleanup before it hands off), asks name/tier/language with `gum` (same tool and prompt styling as Omarchy's own first-boot form), then calls `omarchy-kids-bootstrap`. Tier choices come from `omarchy-kids-set-tier`'s own sibling-directory resolution, so a new tier only needs adding in one place.
- **Also fixes a permanent-autologin gap found while researching this**: Omarchy's own first-boot installs a one-shot service that removes SDDM autologin after the first boot on unencrypted installs (the disk isn't meant to stay auto-unlocked past the owner's first login). For the mini tier that's the wrong default — the kiosk's whole security model is "no reachable login prompt" (see root CLAUDE.md's kiosk-lockdown principle, already enforced twice elsewhere: VT-switch masking, hiding the Omarchy top bar's menu icon), and a normal SDDM greeter is exactly that kind of escape hatch. The wizard now removes that one-shot cleanup unit, so autologin stays permanent for the mini tier the same way it already does for encrypted installs.
- **The wizard now also invokes pairing (issues #22/#23 wiring, 2026-08-29)**: after bootstrap, `run_pairing` calls `sudo -u <child_user> omarchy-kids-pairing serve --port 7420 --timeout-minutes 10`, opening/closing a UFW rule for the pairing port around the call (found missing during pairing verification, see `docs/agent-protocol.md` — no sudoers workaround needed here, unlike `grant_getty_lockdown_sudo`, since the wizard already runs as root). `serve` itself prints the pairing code and a terminal-renderable QR code to stdout, so tty1 — already the child's screen at this point — is all that's needed to "show" it, no extra rendering required. **Deliberately best-effort, not a hard requirement for setup to complete**: the Control Center this is meant to pair with doesn't exist yet (`control/` is still a stub), so blocking first boot on a successful pairing would mean setup never finishes for anyone today. A skipped (Ctrl+C), timed-out, or failed attempt is logged as a warning and setup continues — no marker-gated retry loop here, re-pairing later is a manual `omarchy-kids-pairing serve` re-run (retry UX is issue #25, intentionally not built here).
- **Verification status (2026-08-29): logic-level plus a real pairing round-trip, not a full first-boot run.** `detect_child_user` and `discover_tiers` were exercised against the dev VM's real state — `discover_tiers` correctly found `mini`; `detect_child_user` correctly refused with both `devchild` and `omarchy-kids-parent` present (the VM's actual post-Phase-1 state — genuinely ambiguous, so refusing is the right call) and was separately confirmed to pick the lone candidate correctly against a synthetic single-account `/etc/passwd`. `disable_autologin_once_cleanup`'s target paths were confirmed absent on this VM (it's disk-encrypted, so Omarchy's own first-boot never installs that cleanup unit there in the first place — see the bullet above). The UFW open/close functions and the `sudo -u <child_user> omarchy-kids-pairing serve` invocation itself were run for real against the VM — a full `serve`/`pair` round trip over `sudo -u devchild` correctly installed a `command=`-restricted key into `/home/devchild/.ssh/authorized_keys` with correct ownership, and a `SIGINT` mid-`serve` (simulating Ctrl+C) exits non-zero as the wizard's best-effort handling expects. Not exercised: the `gum` prompts end-to-end (no non-interactive way to drive a TUI picker over plain SSH) and the systemd unit itself against a real `omarchy-provision-owner.service` run — that needs a fresh deferred-provisioning install, which would discard this VM's already-verified Phase 1 state, so it wasn't done without checking first.
- Not yet done: packaging `tiers/` (see its README) — both the bootstrap dev-VM verification and this hook assume `omarchy-kids-set-tier`/`omarchy-kids-bootstrap`/`omarchy-kids-pairing` are already on `PATH`, since the script resolves sibling tier directories relative to its own (symlink-resolved) location.
